# B005 — alternating records and interruption recovery

## Purpose and limits

B004 established a single-card baseline of 10,000 successful changing-data write/read pairs and ten fresh-launch read-only sessions. B005 tests whether keeping the previous valid record in a separate preallocated file can recover from an incomplete update. This is a CPU-free probe; Tau's VexRiscv integration follows only after physical recovery evidence.

Simulation, mock JTAG and host checks pass. Physical B005 results are pending. Neither a command completion nor a valid CRC establishes power-loss durability. Two files can share filesystem/card failure modes. CRC detects accidental corruption; it supplies no cryptographic authentication or protection against malicious replacement/replay. Generation ordering requires a trustworthy preserved prior record.

## Fixed format and commit rule

Configuration: experiments/b005.json. Two existing 8,192-byte files, recover-b005-a.bin and recover-b005-b.bin, map to slots 0x25 and 0x26. All bytes outside the 512-byte record at offset 512 must remain 0xA5. No file creation, resizing, FAT manipulation or raw-sector access occurs in the core.

The record has eight big-endian 32-bit header words: magic SDR5, version/header size 0x00010020, record size 512, generation high/low, payload length 480, zero reserved flags, CRC32. CRC-32/ISO-HDLC covers bytes 0–27 and 32–511, excluding the stored CRC. Generation is unsigned 64-bit, nonzero, and cannot wrap. Equal generations must contain identical records; otherwise recovery stops with a conflict.

Before writing, read and validate both records. Preserve the latest valid file and update the older/invalid one using four 128-byte writes. Read all 512 bytes back and require the exact generated bytes plus valid header/CRC before publishing the new generation. Missing words, command errors, mismatch or timeout stop the session. Timeout never releases an outstanding command, even if completion/reset/buttons arrive later. This protocol does not provide an SD flush primitive. Clean mode initializes generation 1 when neither record validates; B005 does not distinguish a blank pair from a damaged nonblank pair. After an unexpected NO VALID result, preserve both raw files and stop writes. Recovery has failed in that case; starting a new save would overwrite forensic bytes. A later production policy must require explicit initialization or refuse damaged nonblank pairs.

## First clean batch

1. Insert the safely ejected card and freshly load the stable CARDWRITE02 entry. Confirm **B005**, metadata **0.5.0**, READY, zero commands. Record firmware (currently reported 2.7), card identity and exact actions.
2. Keep power on and leave buttons untouched for JTAG-controlled testing. The host must not have CARDWRITE mounted. Capture `python3 tools/jtag_recovery.py status`, then `start`, then `results`.
3. Expected first clean result: PASS, 64 verified commits, 322 commands, valid mask 3, A generation 63, B generation 64. Preserve all 64 retained JTAG records and a screenshot. LCD generation shows the low 32 bits; JTAG/host compare the complete 64 bits.
4. Quit normally and mount the card. Run `python3 tools/read_recovery_results.py --test-id RECOVERY-005-CLEAN01 --firmware 2.7 --generation 64 --generation-a 63 --generation-b 64 --generated`. Verify both exact records, all guards and every prior protected file. Review any newly added runtime files/screenshots explicitly.
5. Eject, freshly launch B005, capture `status`, `cold`, `results`. This must issue exactly two reads, zero writes, select generation 64 and PASS. After remount use a new ID and `--read-only-baseline RECOVERY-005-CLEAN01` with generation 64. Require both files and every existing protected file unchanged. Separately record whether this was an actual full power-off; a remount alone does not establish that.

A starts the same 64-commit batch; B starts read-only recovery. Each session starts only once; reload for another session. Later clean batches continue from the saved generation instead of resetting fixtures.

## Controlled interruption discovery

Begin only after the first clean batch and recovery pass. Before the first intentional interruption, make and hash-verify a complete backup of the card's non-OS contents, retaining snapshots and all physical outputs. Verify free space and card identity. Do not automatically repair/reinitialize a damaged filesystem; preserve it as failure evidence. These tests intentionally cut power on the designated disposable research card.

For each point 0, 1, 2, 3, use a fresh B005 launch and capture the selected prior generation G. `python3 tools/jtag_recovery.py pause --point N` requests exactly one update, pausing before the first chunk (0) or after 128/256/384 bytes (1/2/3). Capture PAUSED status and its full JTAG snapshot, selected generations, destination, counters and screenshot before cutting power. This is a known boundary between commands, not a claim of interruption during an SD command.

A Pocket power-button shutdown may be orderly. Record the actual mechanism and classify it accordingly; do not label it abrupt power loss without evidence. JTAG reconfiguration alone is not an SD power cut. During-command power-loss qualification requires a separately controlled disruption mechanism. The PAUSED generation/validity fields describe cached boot/committed records; the partially written destination must be validated from its physical bytes after remount.

Two separate trials at each point:

- **Resume control:** request `resume`, collect `results`, then normal Quit/remount. Expect one committed generation G+1, seven commands, full-byte record/guard validation, and the previous latest file unchanged.
- **Power interruption:** explicitly power off at PAUSED without resuming or normal Quit. Record the exact power action and time. Mount and preserve both raw files before any new core writes. The host oracle must recover G; a fully valid G+1 is also acceptable only if observed bytes justify it. Never accept a higher generation with invalid header/CRC or changed guards. The previous latest file must be byte-identical. Freshly launch and run `cold`; select the same host-validated latest generation with two reads and zero writes. Remount and prove the cold read changed neither record nor any protected file.

Use separate immutable trial IDs, including phase, control/cut, repetition and expected generation. Initial discovery is one control and one cut per point. Only after discovery passes, expand to at least 20 explicitly confirmed power cuts per point; retain every failure and denominator. Increase duration/cards/filesystem variants before making a broad repeatability claim.

## Later qualification matrix

| Area | Required evidence |
| --- | --- |
| During-command interruption | Fresh qualified instrumentation/build to cut during each chunk and final verification read; record issued/acknowledged/complete boundaries |
| Corrupt records | Damaged magic/version/length/flags/CRC/payload, incomplete reads, equal-generation conflict, both invalid; immutable fixtures and expected recovery |
| Generation boundaries | 32-bit carry, maximum 64-bit generation refusal, equal identical records, stale valid record selection |
| Storage failures | Removal, full card, fragmented existing files, wrong/missing slot, read-only media; preserve last valid record and stop on failure |
| Lifecycle | Explicit full power cycles, normal Quit/reload, reset while command outstanding, delayed completion; no hidden retries |
| Tau integration | Same format through VexRiscv, cache/DMA/byte-order boundaries, concurrent audio/video loads, save-size and lifecycle requirements from TAU_TEST_MATRIX.md |
| Security | Bounds and slot isolation, reject malformed lengths/flags, no path/raw-sector writes, rollback policy; add authenticated records only if an actual hostile-modification requirement is defined |
| Repeatability | Multiple cards/controllers, firmware versions and filesystem layouts, long campaign with all failure counts and protected-content hashes |

The four prefix-cut simulations, real command-module/serial-bridge simulations, and mock tool tests establish implementation expectations. They do not substitute for these physical trials.
