# Batch experiments after the transfer baseline

## Why batch

A fixed, independently verified transport baseline makes it possible to compare many cases in one Pocket session. FPGA compilation should be needed for changes to the transport or CPU architecture, rather than for every payload size or pattern. CARDWRITE02 is the transport repair gate; it does not yet implement an automatic batch.

## First automatic batch core

Use the stable active core ID `alfatreze.CARDWRITE02`, with a unique B003 build banner/version, and a new dedicated preallocated 256 KiB scratch file, with 32 independent 8 KiB regions. Archive the qualified minimal02 package before a verified update; retain its existing write64.bin untouched. Every case owns its own region; surrounding guard bytes remain known. All source buffers stay in the core's own BRAM. One command owner runs cases serially. A timeout stops the batch and retains outstanding ownership; it must not advance into a new case.

Each case records build ID, run generation, case ID, file offset, requested length, overwrite ordinal, command result, immediate comparison result and elapsed cycles. A summary screen shows passed/failed/completed counts. With the confirmed JTAG link, add a small ISSP control/status block and a stable per-case result window so the host can start a batch and read retained results; use a coherent snapshot/index handshake rather than polling transient bus signals. This instrumentation needs a separately qualified build. The raw file and screenshots are retained on the computer; the host independently reconstructs all expected bytes and guards and compares the whole file. A case's error is retained even if a later retry works.

| Case family | Initial cases | Host check |
|---|---|---|
| Small lengths | 1, 3, 4, 5, 63, 64, 65 bytes | Exact bytes; adjacent guard bytes untouched |
| Sector/block sizes | 511, 512, 513, 1,024, 4,096 bytes | Exact first/last words and complete payload |
| File offsets | Within region; offsets modulo 512 of 0, 1, 4, 508 and 511 | Correct file position and guards; cross-sector cases |
| Payload patterns | Zero, all ones, alternating bits, ascending bytes, deterministic mixed bytes | Entire payload, not only header/checksum |
| Repeated overwrite | Several distinct generations in one region | Immediate compare after each; final durable generation on host |
| Independent records | Disjoint case regions | No cross-case contamination |
| Length changes | Large payload followed by smaller payload at same offset | Correct requested range; known remainder untouched |

These dimensions form a larger candidate catalogue, not a full Cartesian product in the first 32-case run. Select 32 representative combinations after the baseline passes; then expand with separate run generations. File creation, resizing, nonvolatile Quit save and explicit flush are separate method batches with their own expected file semantics.

## Three kinds of result

1. **Command completion:** the firmware returned a result. Recorded per operation.
2. **Immediate byte readback:** each operation compares independently generated bytes inside the core. Still not proof of physical persistence. Earlier versions of an overwritten region cannot all be inspected on the final card file.
3. **Host persistence:** after normal Quit/shutdown and remount, the computer checks every final case region and all guards, plus protected card contents. For independent persistent samples, use distinct regions rather than repeatedly overwriting a single record.

Do not count 32 cases as 32 durable successes if they share a single overwritten final record. Do not call an immediate pass a power-loss guarantee.

## Physical boundaries remain separate

- A successful batch is followed by a cold-launch read-only batch, without writing again.
- Reset, Quit, shutdown, sleep and power interruption need separately recorded physical actions. A core cannot prove its own survival across power removal while continuing the same live session.
- Failure handling and intentionally invalid requests begin with simulation; hardware cases remain bounded to the dedicated scratch file.
- A/B commit protocols and append records need their own recovery batches. An interrupted outcome must be an explicitly allowed prior/new record or a detected incomplete record, never silently accepted corruption.

## After initial coverage

Expand to automated serial stress of at least 10,000 operations and the research plan's cold-cycle qualification, across card/firmware combinations. Bring in the exact Tau VexRiscv configuration after the CPU-free method passes; apply the same record oracle and file guards under Tau workloads. Reuse TAU_TEST_MATRIX.md IDs in each batch manifest.
